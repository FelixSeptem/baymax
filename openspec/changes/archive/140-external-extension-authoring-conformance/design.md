## Context

The existing `extension` package validates descriptors, resolves deterministic resource winners, negotiates capabilities, admits resources, executes bounded lifecycle actions, and isolates activation generations. Existing integration replay covers only a small lifecycle slice. The roadmap requires the next increment to improve external authoring feedback while reusing these owners and preserving the library-first boundary.

The conformance surface must be offline and deterministic. It must consume source-owned projections rather than execute arbitrary extension code, start network services, or create a new lifecycle/session/terminal state machine. Diagnostics continue to be written only through `observability/event.RuntimeRecorder`; replay remains an offline, side-effect-free consumer.

## Goals / Non-Goals

**Goals:**

- Define a stable case schema that an extension author or adapter maintainer can run without a live provider, registry, workspace, or hosted control plane.
- Exercise the complete admission-to-reload boundary using existing extension governance APIs and explicit policy/sandbox/allowlist decisions.
- Produce deterministic, bounded feedback: case identity, contract phase, stable reason code, offending field (when applicable), expected/actual classification, and a remediation hint.
- Verify Run/Stream equivalence, replay idempotency, fixture ordering, and shell/PowerShell gate parity.
- Make regressions actionable without changing runtime semantics by default.

**Non-Goals:**

- No package manager, extension marketplace, remote registry, dynamic download, signing service, or authoring CLI.
- No execution of untrusted extension source as part of the harness; lifecycle execution uses controlled test actions and fault injection.
- No new extension state machine, queue, scheduler, session/artifact store, terminal arbiter, or provider-neutral wire protocol.
- No new runtime configuration keys, credential storage, workspace/Git integration, or `examples/agent-modes` behavior change.

## Decisions

### 1. Use a versioned declarative case schema

Each case records a profile version, bounded case name, descriptor candidates, admission inputs, lifecycle actions, expected outcome, and optional policy/sandbox boundary assertions. Inputs are canonicalized before evaluation; map keys and candidate lists have explicit stable ordering. Unknown additive fields are ignored for forward compatibility, while malformed required fields fail fast with a schema reason.

**Alternative considered:** accepting arbitrary Go callbacks as the public harness API. Rejected because callbacks are not portable, cannot be replayed safely, and make author feedback dependent on implementation details.

### 2. Evaluate through adapters at existing ownership boundaries

The harness invokes descriptor validation/resolution, capability negotiation, admission, bounded execution, generation management, and recorder/replay projections through narrow adapter functions. It never mutates source runtime state and never treats a conformance result as a Run terminal outcome. Policy, sandbox, allowlist, and egress assertions are supplied as source-owned decisions and are checked for non-bypass rather than reimplemented.

**Alternative considered:** embedding a second “authoring runtime” that loads and runs extensions. Rejected because it would duplicate lifecycle semantics and create a bypass path around readiness and sandbox owners.

### 3. Separate contract result from remediation feedback

The canonical result has `status` (`passed|failed`), `phase`, `reason_code`, `field`, `expected`, `actual`, and bounded `remediation`. A failed case is still a deterministic result, not a Go panic or process-dependent error string. Remediation text is derived from a fixed reason-to-guidance table so wording and ordering remain replayable.

**Alternative considered:** exposing raw error strings. Rejected because strings drift across platforms and leak implementation details; stable reason codes already exist in extension and adapter contracts.

### 4. Keep fixtures and replay separate from runtime diagnostics

Fixtures live under integration testdata and are normalized by `tool/diagnosticsreplay` without writing diagnostics or executing side effects. Runtime lifecycle observations, when generated by integration tests, use `RuntimeRecorder` and only bounded additive fields. Replay compares canonical results, not raw source or payload bodies.

**Alternative considered:** persisting full extension manifests or source snapshots in diagnostics. Rejected for privacy, size, and source-of-truth reasons.

### 5. Gate in both shell environments with one semantic profile

One semantic profile name (for example `external_extension_authoring.v1`) drives Go replay tests and dedicated `.sh`/`.ps1` wrappers. The wrappers invoke the same focused test selection and classify failures consistently. The quality gate calls both platform-appropriate paths, while CI can promote the conformance job to a required check later.

## Data Flow

`case fixture -> canonical decode/validation -> source resolution -> manifest/capability admission -> controlled lifecycle/fault action -> bounded conformance result -> replay normalization -> shell/PowerShell gate`

At every step, rejected candidates produce no activation side effect; a failed reload retains the prior generation; stale generation events are suppressed; and a conformance failure cannot overwrite the authoritative Run/Stream terminal result.

## Risks / Trade-offs

- [Risk] The case schema becomes an accidental second extension API. → Mitigation: keep it testdata-oriented, transport-neutral, versioned, and explicitly non-executable; expose only bounded result types.
- [Risk] Remediation guidance drifts from reason taxonomy. → Mitigation: derive guidance from a fixed table and add replay assertions for every reason code.
- [Risk] Fixtures overfit current implementation details. → Mitigation: assert observable contract outcomes and phase/reason classifications, not internal function names or error text.
- [Risk] Cross-platform gate output differs. → Mitigation: canonical JSON normalization, stable ordering, shared test selection, and shell/PowerShell parity tests.
- [Risk] A real drift requires runtime code changes and expands scope. → Mitigation: fixture-first triage; only additive, minimal fixes at the owning package are allowed, with explicit rollback and full regression gates.

## Migration Plan

1. Add the case schema, canonicalizer, and initial fixtures without changing runtime behavior.
2. Add harness adapters and contract/replay tests, then wire dedicated shell/PowerShell gates into quality checks.
3. Update docs and roadmap to record the active change and evidence.
4. If a fixture exposes drift, apply the smallest owner-local correction and add a regression fixture; otherwise ship as test/fixture/gate/doc-only.
5. Rollback by removing the new harness, fixtures, gate wiring, and additive documentation. No data or configuration migration is required; existing extension lifecycle behavior remains available.
