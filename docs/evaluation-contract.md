# Bounded Evaluation Contract

Baymax's bounded harness candidate comparison is an offline evaluation contract, not a runtime execution or recovery capability. The versioned `candidate_experiment.v1` manifest binds a reproducible corpus item and rubric, model, authority and data digests, budget, offline network policy, baseline, candidate assets, and allowed asset surface.

Candidate admission validates normalized relative paths, explicit path roots, per-asset and surface byte limits, semantic candidate identities, and declared static-check results before probe evidence may be selected. The baseline remains eligible even when no candidate has acceptable probe evidence. A same-ID experiment with changed configuration or asset digests is identity drift and must not be merged.

Selection is committed from probe evidence before final scoring. Selection inputs do not include scoring-only data. Scoring is a separate `candidate_comparison.v1` fact and preserves `unscored`, `unavailable`, and `insufficient-evidence`; missing scores are never converted to zero. Reports retain separate quality, reliability, contract, latency, and cost axes, and account for attempts, retries, cache hits, model calls, cost, and incomplete attempts.

Replay in `tool/diagnosticsreplay` is a pure, bounded reduction over versioned evidence. It does not call providers, tools, networks, production execution, or recovery APIs. Outputs are review-only: they cannot publish or activate candidate assets or mutate prompts, Skills, tools, policy, memory, configuration, code, tests, gates, or a long-term experience library. A reproducible owner gap must be routed through a separately reviewed OpenSpec change.

Validation: `pwsh -File scripts/check-candidate-comparison-contract.ps1`, `bash scripts/check-candidate-comparison-contract.sh`, and `go test ./runtime/evalcontract ./tool/diagnosticsreplay -count=1`.

The public entry points are `NormalizeCandidateExperiment`, `CompareCandidateIdentity`, `AdmitCandidateWithValidation`, `SelectCandidate`, and `BuildCandidateComparison` in `runtime/evalcontract`. Normalization returns a SHA-256 digest without modifying caller-owned slices. Admission must complete before an external offline evaluator probes candidates; replay rechecks candidate identity, scope and declared static-validation results. The normalized allowed paths are the candidate asset write scope. No API grants production write authority or executes a probe.

`BuildCandidateComparison` requires the admitted experiment digest, `network_verified=true`, `scoring_data_status=isolated`, and nonempty `network_evidence_ref` / `scoring_isolation_evidence_ref`. The external evaluator owns actual egress and scoring-data isolation; these references identify its retained enforcement evidence. The reducer checks recorded facts and never opens the references or claims to create a sandbox. A missing or unknown isolation state fails closed. Only the offline network policy is currently supported.

The committed selection must have a positive sequence; final scoring must have a greater sequence. These sequences describe evaluation stages within one experiment and do not assert native source event ordering. Baseline may be selected conservatively even when a candidate has stronger probe evidence. Probe quality and final score use nullable numeric values, so an actual zero is distinguishable from missing evidence. An `available` final score requires a numeric value and scoring digest; other scoring states reject numeric values.

Attempt evidence uses `(candidate_id, attempt, retry)`; omitted run attempt means attempt 1 and retry defaults to 0. Repeated probes use distinct attempts and retry records use their causal retry ordinal. Duplicate run keys or ledger keys fail closed. `attempt_total` counts ledger records including retries; `retry_total` counts records whose retry ordinal is positive, rather than summing ordinal values. `incomplete_total` counts failed and incomplete ledger records. Results retain the run evidence, per-attempt ledger and isolation evidence references alongside totals. Missing ledger coverage for any recorded run produces an `insufficient-evidence` cost axis with no numeric value; recorded totals remain partial accounting. Explicit failed/incomplete attempts with accounted costs remain visible and do not erase costs already incurred. Negative or overflowing cost accounting is rejected.

Fixture coverage is versioned under `tool/diagnosticsreplay/testdata/candidate_comparison_*.v1.json`: success, identity drift, scope rejection, isolation unavailable, scoring unavailable, incomplete cost, and baseline selected. Success fixtures assert all five outcome axes and accounting totals; error fixtures require an exact nonempty classification. Tests also cover repeated replay idempotency, selection/scoring order, deliberate output drift, and the preexisting `evaluation_contract.v1` legacy payload independently of the new fixture namespace. The PowerShell gate accepts `-FixturePath <path>` and the shell gate accepts a fixture path as its first argument, allowing intentional drift to demonstrate a nonzero exit.

Quality and latency sums reject integer overflow or underflow with `candidate_evidence_unavailable`. A run and ledger record for the same attempt must agree on execution status; a contradiction returns `candidate_cost_ledger_drift`. Ledger-only attempts remain valid accounting for executions without probe evidence.

Stable rejection classifications include `candidate_experiment_malformed`, `candidate_experiment_identity_drift`, `candidate_asset_scope_rejected`, `candidate_isolation_unavailable`, `candidate_evidence_unavailable`, `candidate_selection_drift`, `candidate_scoring_order_drift`, `candidate_cost_ledger_drift`, `candidate_run_conflict`, `candidate_comparison_version_drift`, and `candidate_network_policy_unsupported`. A replay expectation mismatch returns `candidate_comparison_non_actionable`, or the evidence/cost classification for an outcome-axis/accounting mismatch.

No runtime configuration keys, defaults, hot-reload behavior, RuntimeRecorder schema, CLI or production integration entry points change.
